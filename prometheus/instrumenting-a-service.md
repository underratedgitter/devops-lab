# Instrumenting a service with Prometheus

Notes from wiring Prometheus into a Node service and running it against a real cloud deployment. The examples are from [CI-CD-Pipeline-Automation](https://github.com/underratedgitter/CI-CD-Pipeline-Automation-with-Docker-Cloud-Deployment).

---

## The four metric types, and when each is wrong

| Type | Use for | Gets misused as |
|---|---|---|
| **Counter** | things that only go up — requests, errors | a gauge, by people who reset it |
| **Gauge** | things that go up and down — in-flight requests, memory | a counter, losing history |
| **Histogram** | distributions you want quantiles from — latency | a gauge holding an average |
| **Summary** | quantiles computed client-side | a histogram, when you needed to aggregate across instances |

The mistake worth avoiding is **average latency**. An average of 200ms hides that 1% of users wait four seconds. A histogram keeps the buckets, so `histogram_quantile` can give you p99 after the fact — and p99 is what people actually feel.

```js
const httpRequestDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'Duration of HTTP requests in seconds',
  labelNames: ['method', 'route', 'status_code'],
});
```

## Naming

`http_request_duration_seconds`, not `requestTime`. The convention is `<namespace>_<subject>_<unit>`, always base units — seconds not milliseconds, bytes not megabytes. Grafana and every example query on the internet assume it.

Suffix rules that tooling depends on: `_total` for counters, `_seconds`/`_bytes` for units, `_bucket`/`_sum`/`_count` are generated by histograms — never write them yourself.

## Labels are a cardinality budget

Every distinct label combination is a separate time series. `route` is fine — a handful of values. `user_id` will kill the server.

```js
// fine: bounded set
labelNames: ['method', 'route', 'status_code']

// disaster: unbounded
labelNames: ['user_id', 'request_id']
```

The rule: if you can't write down every possible value, it isn't a label. Put it in a log line instead.

## Scrape configuration

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:
  - 'alert_rules.yml'

scrape_configs:
  - job_name: 'render-app'
    scheme: https
    metrics_path: '/metrics'
    static_configs:
      - targets: ['your-app.onrender.com']
```

`scrape_interval` sets the resolution of everything downstream. 15s is a reasonable default: fine enough to see a spike, coarse enough that a year of data doesn't need a storage plan.

`evaluation_interval` is how often alert rules run. Keeping it equal to the scrape interval avoids evaluating a rule twice against the same sample.

### A trap I walked into

Job names in scrape config and job names in alert expressions have to match. This alert:

```yaml
- alert: AppDown
  expr: up{job="node-app"} == 0
```

can never fire if the only scrape job is called `render-app`. The rule is not wrong, and Prometheus reports no error — the selector simply matches nothing, forever. **A silent alert is worse than no alert**, because you believe you are covered.

Check with:

```promql
up
```

in the Prometheus expression browser. Every job you expect should appear. If a job name is missing there, every alert referencing it is dead.

## Exposing metrics

```js
app.get('/metrics', async (_req, res) => {
  res.set('Content-Type', client.register.contentType);
  res.end(await client.register.metrics());
});
```

Two things worth doing:

**Exempt `/metrics` from rate limiting.** A limiter that throttles your own scrape turns a traffic spike into a monitoring blackout at exactly the moment you need visibility.

**Register the default collectors.** `client.collectDefaultMetrics()` gives you heap, RSS, event-loop lag and GC pauses for free — event-loop lag in particular is the single best indicator that a Node process is in trouble.

## An info metric for correlating deploys

```js
const appInfo = new client.Gauge({
  name: 'nodejs_app_info',
  help: 'Application version and environment',
  labelNames: ['version', 'node_version', 'environment'],
});
appInfo.set({ version: VERSION, environment: NODE_ENV }, 1);
```

A gauge permanently set to 1, carrying information in its labels. It looks pointless until an error rate jumps and you can overlay it to see the version changed at the same moment.

## Checking your work

Before trusting a dashboard, generate load. Metrics against zero traffic all read zero and tell you nothing about whether the instrumentation is right.

```bash
npm run traffic     # drives requests so histograms fill and gauges move
```

Then confirm in the expression browser that each metric exists, has the labels you expect, and moves when it should.
